# Task 42 — Package RPM for ReaPack with a tag-driven index

Target: claude

## Goal
Make ReaperPluginManager installable and updatable through ReaPack from this
repository (github.com/Diebanez/ReaperPluginManager, branch `master`): ReaPack
package headers on the scripts, a reapack-index configuration, and GitHub
Actions that validate the package on every push and, on every pushed `v*`
tag, run `reapack-index` and commit the updated `index.xml` to `master`.
Releasing is then: bump `@version` in the package header, tag that commit
`v<version>`, push.

## Acceptance criteria
- `RPM_Setup.lua` is the one package file. Its header, at the top of the
  file and using only tags reapack-index's packaging documentation defines,
  carries `@description` (shown as the package's name in ReaPack), `@author`,
  `@version 1.0.0`, an `@about` of a few lines, and `@provides` listing:
  `[main] RPM_Watcher.lua`, `[main] RPM_CheckProject.lua`,
  `[main] RPM_CatalogueManager.lua`, and, without `[main]`, `rpm_core.lua`,
  `rpm_reaper.lua`, `helpers/rpm-install.ps1`, `helpers/rpm-install.sh`,
  `helpers/rpm-secret.ps1`, `helpers/rpm-secret.sh` and
  `helpers/rpm-run-hidden.ps1`. The package file itself is registered in the
  Action list by ReaPack's default, so all four actions land in the main
  section and nothing else does.
- `RPM_Watcher.lua`, `RPM_CheckProject.lua`, `RPM_CatalogueManager.lua`,
  `rpm_core.lua` and `rpm_reaper.lua` each carry `@noindex`, so the index
  holds exactly one package.
- Every provided file installs at the same path relative to `RPM_Setup.lua`
  as in the repository, so `script_dir`, `helpers_dir()`, the `require`
  path set-up and the startup hook's watcher path keep working unchanged.
  The install folder is `<resource path>/Scripts/ReaperPluginManager/Scripts/ReaperPluginManager/`
  (index name, then the category reapack-index derives from the package
  file's directory).
- `.reapack-index.conf` at the root sets the index name
  `ReaperPluginManager`, `--about README.md`, and a commit template for the
  index commit whose subject follows the repo's imperative style.
- A check workflow under `.github/workflows/` runs on pushes to `master` and
  on pull requests: it runs `reapack-index --check`, then a dry-run scan
  (`--no-commit`, full history) whose resulting `index.xml` is printed to the
  log and never committed.
- A release workflow under `.github/workflows/` runs on every pushed tag
  matching `v*`, with `contents: write`. It checks out `master` with full
  history and fails, committing nothing, unless: the tag names the
  `@version` the tagged commit's `RPM_Setup.lua` carries; no file under
  `Scripts/ReaperPluginManager/` changed between the commit that introduced
  that `@version` and the tagged commit; and `master` holds no later
  `@version` change than the tagged one. It then runs
  `reapack-index --commit` and pushes the index commit to `master`.
- Both workflows pin every action to a full commit SHA (with its version in
  a comment), pin the Ruby version, install `reapack-index` 1.2.6 exactly
  (`gem install reapack-index -v 1.2.6`), and install Pandoc for `--about`,
  following cfillion's reapack-repository-template workflows (`check.yml`,
  `deploy.yml`).
- `reapack-index --check` and a dry-run scan with gem 1.2.6 pass (locally or
  in the check workflow), and the dry-run index shows one package,
  `RPM_Setup.lua` in category `Scripts/ReaperPluginManager`, version 1.0.0,
  with the four action scripts as `main` sources, the other seven files as
  plain sources, nothing from `.claude/`, `server/` or the repository root,
  and source URLs of the form
  `https://github.com/Diebanez/ReaperPluginManager/raw/<commit>/Scripts/ReaperPluginManager/...`.
- No tag is created or pushed, and the repository's visibility is not
  changed (`gh repo edit --visibility` is never run).

## Decisions
- **ReaPack distribution (user decision, 2026-10-23).** The repository will be
  made public by the user, separately and after an audit; this task assumes
  it is still private. The index's raw URLs resolve only once it is public,
  so the package is verified through reapack-index's own check and dry-run
  scan, not by installing it in REAPER.
- **index.xml from a GitHub Action on `v*` tags (user decision,
  2026-10-23),** using cfillion's `reapack-index` gem and its documented CI
  shape (reapack-repository-template); action and gem versions pinned.
- **`RPM_Setup.lua` is the package file**, because Setup is what a user runs
  first; the version lives in its header alone.
- **The release workflow's guards** exist because reapack-index pins each
  version's file URLs to the commit that introduced that `@version`: a tag
  placed after later script changes, or a scan picking up an untagged later
  version on `master`, would publish sources other than the tagged code.
- **The check workflow** validates headers on every push, so a broken header
  is caught before a tag; creating a tag is not this task's job.
- **One package for Windows and macOS, with no platform tags.** The user
  allowed the two platforms to share one package (2026-10-23); every helper
  then installs on every platform, which costs a few small files and avoids
  a helper missing under a platform string ReaPack reports unexpectedly. On
  Linux the manager does nothing, as it already does.
- **Repository layout unchanged.** The install folder repeats
  `Scripts/ReaperPluginManager` because reapack-index derives the category
  from the package file's directory; moving the scripts would change the
  layout CLAUDE.md and the catalogue-assistant skill rely on, for a cosmetic
  gain.
- **Helpers need no executable bit or line-ending change.** ReaPack does
  not preserve file modes, but `rpm_reaper.lua` runs both `.sh` helpers as
  `/bin/bash <path>` and the `.ps1` helpers through `powershell -File`;
  `.gitattributes` keeps `.sh` files LF and the repository stores every file
  LF, which is what raw URLs serve.
- **Setup keeps registering the actions.** ReaPack registers the four
  scripts in the main section by their installed path; Setup's
  `AddRemoveReaScript(true, 0, path, …)` on the same path keeps the existing
  command id (`setup-action.md` § Architecture: idempotent for an
  already-registered path), Setup needs the watcher's id to start it at once,
  and a hand-copied install has no other registration. `RPM_Setup.lua`'s
  behaviour and `setup-action.md` are unchanged.
- **No ReaImGui dependency.** ReaPack has no dependency mechanism; the
  catalogue editor keeps telling the maintainer to install ReaImGui
  (user decision, 2026-10-23).
- **The catalogue-assistant skill is never in the package** (CLAUDE.md): it
  lies outside the package's folder and is not provided.
