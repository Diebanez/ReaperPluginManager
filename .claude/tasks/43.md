# Task 43 — Document the ReaPack install and release

Target: claude

## Goal
Once task 42 has packaged ReaperPluginManager for ReaPack, bring every
document that describes the zip release up to date: the member-facing
install instructions in `README.md` (installing ReaPack, importing this
repository, installing the package, running Setup, ReaImGui for the
maintainer, updating and removing), the server guide's ReaImGui note, the
release procedure and new files in `CLAUDE.md`, and the domain layer's
statements of how the product is released.

## Acceptance criteria
- `README.md` § *Installing* replaces the zip steps with: install ReaPack
  (reapack.com) if REAPER lacks it; *Extensions > ReaPack > Import
  repositories...* with
  `https://github.com/Diebanez/ReaperPluginManager/raw/master/index.xml`;
  install the ReaperPluginManager package from *Extensions > ReaPack > Browse
  packages*; then run Setup once from the Action list, under the name the
  Action list shows for the ReaPack-registered `RPM_Setup.lua`. It keeps the
  REAPER 7 / Windows 10/11 / macOS requirement and states where the files
  land (`Scripts/ReaperPluginManager/Scripts/ReaperPluginManager/` under the
  resource path).
- `README.md` says that updates arrive through ReaPack's package
  synchronisation, and that removing the package in ReaPack leaves Setup's
  block in `Scripts/__startup.lua`, which the user deletes by hand (it is
  the block between the two markers *What Setup does* names).
- `README.md` tells the maintainer that Catalogue management also needs
  ReaImGui, which ReaPack cannot install as a dependency: install it from
  *Browse packages* (it comes from the ReaTeam Extensions repository, which
  ReaPack includes by default) and restart REAPER. `server/README.md`
  § *ReaImGui* keeps its requirement (version 0.9 or later, members do not
  need it) and cites `README.md` for the installation steps instead of
  repeating them.
- `README.md` points the maintainer to the repository's `server/` folder
  (server setup guide and example catalogue), since the ReaPack package
  carries only the scripts and helpers.
- `CLAUDE.md` § *Layout* names `index.xml` (written by the release workflow,
  never edited by hand), `.reapack-index.conf` and `.github/workflows/`;
  `CLAUDE.md` gains a *Releasing* section stating the procedure — bump
  `@version` (with an `@changelog`) in `RPM_Setup.lua`'s header in the last
  commit that touches `Scripts/ReaperPluginManager/`, tag that commit
  `v<version>`, push `master` and the tag — and the rule that a new file
  under `Scripts/ReaperPluginManager/` is added to the header's `@provides`
  and, when it is a `.lua` file, carries `@noindex`.
- `.claude/domain/technical-direction.md` states the agreed design change —
  the release is a ReaPack package indexed by this repository's
  `index.xml`, which a GitHub Action regenerates on every version tag;
  members install ReaPack, import the repository and run Setup; the server
  guide and example catalogue stay in the public repository; the Claude-based
  catalogue assistant is not in the package — in every passage that stated
  the zip release (§ Hosting and deployment, *Release*). Nothing else in the
  document changes.
- `.claude/domain/features/catalogue-assistant.md` § Scope and non-goals
  names the ReaPack package instead of the release zip. Nothing else in the
  document changes.
- `.claude/domain/design-process.md` states ReaPack wherever it states the
  GitHub zip release (§ Current stage and the *Decisions worth keeping*
  bullets on the zip release and on members' extensions: members need
  ReaPack to install the manager, ReaImGui stays the maintainer's alone).
- No document in the repository still describes the release zip or the
  GitHub releases page as the way to install.

## Decisions
- **Design change agreed (user decision, 2026-10-23):** the release becomes
  a ReaPack package from this repository, with `index.xml` generated by a
  GitHub Action on `v*` tags, replacing the zip on GitHub releases unpacked
  into REAPER's `Scripts` folder (`technical-direction.md` § Hosting and
  deployment); the catalogue assistant is left out of that package rather
  than out of the zip (`catalogue-assistant.md` § Scope and non-goals).
  `technical-direction.md` is normally `/product-design`'s and
  `catalogue-assistant.md` `/architect`'s; this task updates them for exactly
  this and for nothing else. A further design decision met at
  implementation time is not covered: leave that passage untouched and name
  it under *Follow-ups* as a precise follow-up.
- **`design-process.md` follows the same change.** It is `/product-design`'s
  run record, and its decision bullets would otherwise state the zip release
  and "members keep zero extensions", both false once members install
  through ReaPack.
- **`product-design.md` is unchanged.** "The release ships what a group
  needs to set up its own server" stays true of the public repository,
  which keeps `server/`; README points the maintainer there.
- **The release procedure lives in `CLAUDE.md`,** not in `README.md`: it is
  for whoever maintains this repository, while `README.md` is the
  member-facing guide.
- **README documents ReaPack only.** No hand-install alternative is
  described; the GitHub releases page carries no zip.
- **The ReaImGui steps live in `README.md`** (user decision, 2026-10-23:
  README explains installing it through ReaPack); `server/README.md` cites
  them, one rule in one place.
