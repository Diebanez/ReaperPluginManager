# Task 54 — Shared presence detection and platform installer lookup

Target: claude

## Goal
Extract the two lookups the classifier does inline into pure functions the
catalogue browser of feature `catalogue-browser` can call too: the set of
catalogue entries some installed plugin associates with (`present_entries`,
plugin-detection) and the installer an entry has for a platform
(`catalogue.installer`, plugin-catalogue). The classifier calls both, so the
project check and the browser decide presence and installability in exactly
one place.

## Acceptance criteria
- `rpm_core.lua` exposes `present_entries(installed, lookup) → set`: the set,
  keyed by entry, of catalogue entries some plugin of `installed` (each
  `{ name, ident }`) associates with through `lookup`, by the existing
  association order (identifier key, `norm(base name)`, `norm(bare name)`).
  A nil `lookup` yields an empty set. It makes no `reaper.*` call.
- `rpm_core.lua` exposes `catalogue.installer(entry, platform) → installer |
  nil`, beside `catalogue.unmanaged`: the entry's installer object for
  `windows` or `macos`, nil when the installer is absent, JSON null, or the
  entry is malformed. It never raises.
- `classify` calls both functions in place of its inline presence loop and
  inline installer lookup; its output for any input is unchanged.
- No other behaviour of the module changes.

## Decisions
- `present_entries` lives at the module's top level beside `classify` and
  `missing`, the plugin-detection functions; `catalogue.installer` lives in
  the `catalogue` table beside `unmanaged`, as catalogue-browser.md
  § Shared with existing features places them.
